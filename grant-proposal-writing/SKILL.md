# 科研项目申报书写作

根据本次申报要求，将参考材料和研究设想写成适合对应章节、符合承担范围、可以直接使用的申报内容。

本技能按“明确任务 → 整理材料 → 理解写作要求 → 起草修改 → 核对交付”组织工作。这是处理任务的思路，不是申报书的目录。申报书有哪些章节、如何排序、各写多少，均由本次要求决定。局部任务只处理相关步骤，不必重新开展整份本子的写作流程。

以下默认偏好可由用户本次明确要求覆盖。历史项目的章节、技术、金额和成果配额不作为新项目的默认设置。

## 1. 明确本次写作任务

开始新的申报写作任务时，先主动用几个简单问题确认关键要求，得到较明确的指示后再开展依赖这些信息的转换、起草和修改。不能在用户只丢来几个参考文件、笼统要求“生成一份”时直接产出最终稿。可先查看文件清单和模板说明，以便把问题问得具体。

优先一次问清以下事项，措辞保持简短：

1. **负责内容：** 这次主要负责哪些课题、章节或研究内容？
2. **格式要求：** 正文还是表格？有指定目录、句式、篇幅或交付格式吗？
3. **模板调整：** 模板是否允许调整，哪些标题、条目、表格或正文部分可以改？这部分需要用户向老师确认，不能由助手自行推定。尚未确认时保留模板原状，待确认后再进行结构调整。
4. **参考文件：** 文件在哪，哪份是本次模板、哪份是主要底稿，哪些仅供参考？

用户在当前任务中已经明确回答的事项直接采用，不机械重复提问；已具备上述信息时即可行动。后续局部修改沿用已确认要求，只追问发生变化或仍不清楚的关键点。

**确定承担范围。** 区分总项目、课题、研究子内容和本次段落，并逐节判断写作边界。一个子内容可能只需要向汇总稿贡献一个条目；“整个课题”也不等于“整个项目”。按已明确的分工选取内容。前后承接应围绕负责内容内部的研究环节展开，不主动写跨课题承接、联动或外部依赖。例如只负责课题3，就直接说明课题3如何开展研究，不写“为了承接课题5的某项工作，我们……”；也不据此增加接口、联调、差旅等任务或费用。只有用户明确要求写协作关系时才展开；若正式任务书另有必须履行的协作条款，先指出具体冲突，请用户明确处理方式。

**确定修改方式。** 新写、扩写、压缩、局部润色和恢复版本是不同任务。“以某版为主”意味着保留该版的结构与主体；“改一段”只改对应段落。恢复版本时确定恢复对象，保留其他已认可的修改。

**确定工作底稿。** 以用户指定版本为准，编辑前读取当前磁盘文件。持续修改默认更新同一文件，必要时保存内部快照；路径变化先查找实际文件，不凭对话记忆重建全文或另造同名稿。

## 2. 整理材料与提取约束

默认先将本次提供的参考资料转换为Markdown，再基于Markdown写作，最终交付Markdown。已有与原件一致的可用转换稿直接复用；按用户限定的文件、章节、页码或工作表处理，保留原件。转换稿放在用户指定目录，未指定时集中放在项目内。

转换需保留正文、标题关系、表格、数字、单位及必要图示信息，核对缺漏和识别错误。原文与新增标注分开，识别不清之处不补造。查看原始页面是为了准确读取内容，不意味着需要复刻视觉排版。用户只要转换时，完成转换即止；已经要求写作时，继续完成正文。

阅读材料时分清各自的用途：

| 材料或要求 | 决定什么 |
|---|---|
| 用户最新明确的任务与分工 | 本次处理范围和修改目标 |
| 当前项目指南、正式任务要求和目标模板 | 必须满足的约束及内容结构 |
| 用户指定的底稿 | 需要保留、接续或修改的文字与组织方式 |
| 其他项目、单位或论文等参考资料 | 经判断可采用的写法、技术依据或测算参考 |

提取与本次写作有关的硬指标、篇幅、标题、表格列项及事实依据。用户要求与项目硬性约束冲突时指出具体条款，明确处理后再作承诺。文件名和修改时间不能推翻用户指定的版本；参考材料中的单位、业绩、设备、金额和示范点位也不能直接变成本项目事实。

## 3. 理解各部分的写作要求

先判断这一部分要回答什么，再决定写入哪些信息、如何展开。判断依据是本次模板说明、用户要求、上下文和参考段落的实际作用，不能仅凭标题套固定写法。

**内容适配比字数和技术名词数量更重要。** 同一项研究可以出现在不同部分，但应根据用途重新组织信息。研究方案中如果只是罗列研究任务，即使写得很长，也仍然没有说明方案。

下面是判断内容用途的常见参照，不是固定章节清单、排序或通用句式。目标模板将多种用途合在同一节时，按实际要求组合。

| 这一部分需要回答的问题 | 内容应侧重什么 |
|---|---|
| 要研究什么？ | 研究对象、需要开展的任务、任务边界及拟形成的能力；避免提前展开完整实施细节 |
| 为什么这是需要解决的问题？ | 对象特点、困难成因、关键矛盾或瓶颈；科学问题侧重关系与机理，技术问题侧重实现障碍 |
| 准备怎样开展研究？ | 输入基础、关键机制、具体处理关系及输出，使读者理解任务怎样实现；不能只把“研究某内容”换成“采用某技术” |
| 各环节怎样衔接？ | 本次负责内容内部的前后依赖、输入输出和过程关系，避免重复整段方法说明或主动延伸到其他课题 |
| 新意在哪里、为什么可行？ | 创新部分说明相对已有方法的实质区别；可行性部分用已有基础和实施条件支撑，并区分已有成果与拟开展工作 |
| 最终交付什么？ | 明确成果及其内容、功能、数量和适用性能要求，避免只列阈值或凭空增设独立交付物 |
| 能带来什么价值？ | 在本责任范围内说明成果对实际业务的作用，有依据时再量化效益 |

用户提供明确句式时，保留其论述关系和要求的落点。例如要求“对象特点—困难成因—形成某问题—如何突破”时，需让问题名称和最后的突破方向对应同一个矛盾；这种句式只在本次要求适用时采用。

遇到上述参照未涵盖的部分，同样先确定它的用途。不同部分可以共享事实和研究对象，但不能用同一段文字反复替代不同的论述任务。

## 4. 起草与修改正文

按照本次要求的章节结构落笔。模板规定的小标题、顺序和表格列项默认保留，按用户向老师确认后的可调整范围修改；具体研究标题随该部分用途调整，研究对象和承担范围保持一致。内部任务编号只有在目标文本确实需要时才写入正式标题。

**把论述写实。** 用研究对象、机制、处理关系和预期作用说明技术，不靠堆砌算法名或宏大术语充实篇幅。参考论文用于支持判断，将适合本项目的机制写清；文献来源按模板引用要求处理，不把阅读过程当作研究方案。

**按要求控制详略。** 参考稿可提供句式、语气和同级篇幅的参照，不能代替当前项目内容。用户要一段时，通过取舍和压缩形成完整段落；要一个创新点时，不再扩展为多个独立创新点。“最多几页”是上限，“几页左右”是内容量目标，按各部分用途安排篇幅。

**保持局部修改的边界。** 保留用户已改和已删内容，围绕指定问题调整，不顺便重写无关章节。

**将排除要求落实为内容删除，避免防御性写作。** 用户在初稿后说“不要包括A和B”，意思是从下一版正文、表格和预算条目中去掉A和B，并使剩余内容自然连贯。不能把修改指令转写成“本预算说明不包含A和B”“本项目不涉及A和B”“我们不负责A和B”等声明，也不要另加一句强调这些内容被排除。此偏好同样适用于首次起草；只有用户明确要求写范围排除说明，或目标模板必须填写该项时，才单独表述。

修改理由、编辑过程、测算假设和待确认事项放在正文外；模板本身要求说明的依据或归属仍应写清。

涉及以下专项任务时，读取相应参考：

- **指标分配：** 读取[指标分配与成果口径](references/indicator-allocation.md)。用户已要求自行分配时，完成建议分配并回填对应正文，明确建议状态。
- **经费预算：** 读取[预算说明写法与用户偏好](references/budget-writing.md)。按负责单位、锁定科目和目标表格处理，区分真实报价、测算假设和正式采购价格。单纯写研究正文时无需读取。

## 5. 核对并交付

交付前重读实际写入的文件，围绕本次任务核对：

- **要求与范围：** 章节、条目和承担内容是否符合已确认要求，局部修改是否保留了其他已认可内容；是否擅自改动模板或加入跨课题承接。
- **内容适配：** 各部分是否回答了它应回答的问题，有没有用任务罗列代替方案、用成果清单代替效益等情况。
- **事实与数值：** 已有基础、拟研究内容和建议目标是否分清；正文与表格中的数量、单位、上下限、子集和预算算式是否一致。
- **修改落实：** 指定增删是否完整生效，是否把“不要包括”的指令错误写成了正文中的排除声明，用户正在使用的目标文件是否确已更新。

默认交付用户指定的Markdown文件；一句或一段的修改可直接回复Markdown文本。章节结构和句式属于内容要求，仍应遵循；字体、页边距、分页等视觉排版由用户后续处理，除非本轮明确要求其他格式或排版工作。

Markdown不能直接证明实际页数。无排版证据时仅说明篇幅估计，不宣称已满足页数要求，也不为此擅自制作Word或PDF。

随交付简短说明改动范围及仍需确认的事实或建议，不把内部工作规则和检查过程写进申报正文。
